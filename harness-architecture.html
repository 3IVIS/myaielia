BUILD A HARNESS · SYSTEM ANATOMY

Inside the harness.

A harness is a governance and reliability control plane around an autonomous agent: the agent has intelligence, the harness has authority. The agent proposes; the harness decides what's allowed to happen next; evidence decides whether the result is accepted. Every non-trivial turn walks the same eleven layers of it, in the same order, whether it's Aielia (Build A Harness's own reference chat agent) or a flow drawn on the canvas. This is that loop — World Model through Reviewer Pass — read out of the harness source (packages/harness, with its Python twin in adapter/harness/). Click any layer below to open its internal flowchart.

THE LOOP

Eleven layers, in the order they run.

The chart follows one non-trivial turn in the order the harness actually executes it. Before the loop the assistant's adaptive layer control decides how much of the harness the turn needs, and the harness initializes its state. Then every iteration thinks (contradiction check, hypotheses, diagnostics, control state, planning), acts (the execution gate, the tool call, then the evidence and world model are updated from what came back) and checks (diagnostics and control state re-scored, verification, and recovery if the task failed), and repeats until every task is complete. The reviewer pass runs once after the loop, and again if it reopens a task; then the answer is validated. Layers keep the numbers used in the code and docs, drawn in execution order. Click any layer, or any 🤖 hook, for its own flowchart.

Skipped on trivial turns

A single consolidated call up front (adaptive layer control) (risk, triviality, decomposition, plan-abandonment, plan-template matching) flags a genuinely self-contained factual one-liner as trivial — that reply returns directly and none of the eleven layers above run. Everything else walks the full loop. See Aielia for how this applies turn by turn in the reference chat agent.

AROUND THE LOOP

One turn, everything on.

The eleven layers above run inside a single proposer loop (ASSISTANT_ONE_LOOP, on by default): the harness drives one tool-calling iteration at a time instead of reviewing a finished reply. Four mechanisms wrap that loop. The diagram shows one turn with all of them enabled: the goal graph decides which thread has focus, the steering channel is polled at the start of every iteration, the Supervisor is consulted only if an iteration stalls, and once the reply is out, up to three next-step options appear under it. What is on by default

All four are on by default in Aielia's CLI and chat-ui (the assistant library itself leaves steering, the goal graph and next-step options off): the one-loop proposer (ASSISTANT_ONE_LOOP), the Trajectory Supervisor (HARNESS_TRAJECTORY_SUPERVISOR), and mid-turn steering with the goal graph (ASSISTANT_GOAL_GRAPH), and the next-step options (ASSISTANT_GOAL_GRAPH_SUGGEST). Each has an explicit disabled (or 0) escape hatch. With steering and the goal graph disabled, a message sent during a turn waits in line exactly as it did before, and no goal graph is kept.

Also by default: the lexical checks under the semantic layers are off (ASSISTANT_LEXICAL_MODE=disabled since 2026-09-28, so contradiction, failure matching and injection detection run on the LLM check alone), the grounding check behind a verified label is on, and so is the semantic judge for caller constraints. Also on: the single retry of a system-error failure (AUDIT_RETRY_SYSTEM_ERRORS), semantic failure matching, resuming a stuck plan only when the message continues it, and the budgeted, priority-ranked facts render with keyed supersession (AUDIT_MEMORY_BUDGETED_RENDER; =0 restores the old 20-fact slice). Off by default, behind AUDIT_* flags: semantic hypotheses, reviewer revision, semantic transcript compaction, experience learning, source reliability, the memory write gate, memory audit log, episodic digests with the recall tool, the memory reviewer and memory consolidation (AUDIT_MEMORY_WRITE_GATE, AUDIT_MEMORY_AUDIT_LOG, AUDIT_EPISODIC_DIGEST, AUDIT_RECALL_TOOL, AUDIT_MEMORY_REVIEWER, AUDIT_MEMORY_CONSOLIDATION), the per-step task-completion check, contradiction severity, code plan templates, retrying every failed task, and ask mode (ASSISTANT_ASK_MODE, which lets the Supervisor and the harness put a structured question to you). The adaptive layer policy is also off: the static policy is the default.

MEMORY

What it remembers, and who may write it.

Memory is separate from the World Model, which is rebuilt empty every turn. Everything that reaches it goes through one service, so no writer can choose its own route: where a candidate lands depends on where it came from, how confident it is, and the configured write mode. By default only the budgeted facts block with keyed corrections is new; the write gate and the cross-turn writers are opt-in and grayed below. Click any box for its details.

on by default opt-in, off by default (flag in the popup)
on by default

Who gets in

A fact you state yourself is kept if it is durable. A model-inferred fact is kept only at high confidence, waits in the pending queue at medium (/memory confirm), and stays session-only at low. With memoryWriteMode=user_only even a high-confidence inference waits for you.

on by default

What the model reads

Each turn the facts are rendered into the system prompt by kind (identity and preference first, then the rest), newest first, until a 4,000-character budget is spent. Facts that do not fit are dropped from that turn and counted, not deleted. AUDIT_MEMORY_BUDGETED_RENDER=0 restores the old last-20 slice.

on by default

Corrections

A fact carries a key for the attribute it describes; a new fact with the same key replaces the old one, which moves to a retired store. Shown on one corrections scenario (3 of 3 seeds, control failed). Keys are chosen by the classifier and are not stable, so a replacement can be missed.

partly opt-in

Safety rails

Memory writes can be stopped entirely with /memory off. Cross-turn writers are staged for your approval by default and nothing is auto-deleted. The write gate (AUDIT_MEMORY_WRITE_GATE) redacts secrets and flags instruction-like text, and fails closed when its check cannot run, but is off by default and showed no outcome gain because the base model already resisted.

opt-in, off by default

Cross-turn writers

Three opt-in writers add what a single turn cannot see: a reviewer (AUDIT_MEMORY_REVIEWER) that proposes memories from repeated behaviour, an episodic digest (AUDIT_EPISODIC_DIGEST) written at the session edge, and consolidation (AUDIT_MEMORY_CONSOLIDATION) that proposes merges and archives, applied only when you accept. In auto mode the reviewer passed 2 of 2 seeds; the digest, 2 seeds on one scenario; consolidation is unmeasured as an outcome.

opt-in, off by default

Recalling past sessions

Digests are never put into the prompt. With AUDIT_RECALL_TOOL on, the model can list or open one through the read-only recall_memory tool, and the result is wrapped as untrusted data. Digests are kept 90 days by default.

What is and is not shown

The corrections behaviour is the only memory change with a demonstrated outcome difference. The write gate, audit log, digest and recall, reviewer and consolidation are mechanisms that work in testing; their value on real use is unmeasured or small-sample, and a plain-language forget request is only staged for your approval (a known gap).

6 Control State

Where it bites in Aielia the harness-level resolver is shown to work at the harness level (4 or fewer executions against 43 without it), but in the assistant its ratio inputs need 3 or more attempted tasks, which the eval notes say Aielia's graphs do not reach. Its effect is delivered instead by a turn-local copy behind the tool-policy gate (a retry loop is blocked once 8 failures are counted, so the 9th attempt is refused) and by the stall rule and Trajectory Supervisor for executor failures.

7 Planning

A task graph with six task states (PENDING, RUNNING, COMPLETE, FAILED, BLOCKED, HUMAN_REQUIRED) and dependency tracking. Ready tasks are picked highest-risk first. Two ready tasks run side by side when neither is HIGH risk and their write domains do not overlap (or overlap with a recorded conflict probability of 0.5 or less). Aielia's tasks declare no write domains, so any two independent ready non-HIGH tasks may run in parallel; a dependency chain or a HIGH-risk task runs serially.

10 Recovery

Six named strategies in a fixed, escalating order — a rollback-and-replan path instead of the run crashing out. In Aielia the strategy picked is mostly bookkeeping (a one-sentence hint reaches the model); what changes the outcome is whether a failed task is retried at all.

Past experience can bias which strategy is tried first, but only when experience learning is switched on (AUDIT_EXPERIENCE_LEARNING=1, off by default). Otherwise nothing writes the strategy weights and this fixed order is always used, as it is whenever the experience store is unavailable (INV-10). A confident (0.7 or higher) failure-mode match that names a preferred strategy jumps straight to it. It ranks below the Supervisor's redirect and, when experience learning is on, below the learned ranking.

system-error retry AUDIT_RETRY_SYSTEM_ERRORS, on by default. Each failed execution is tagged system_error (the executor threw, or the tool or model call broke) or exhausted (it ran out of its own iteration budget). After the ladder switches strategy, a system_error task is re-queued once. Exhausted loops, rejected completion checks and failed verification are never retried, and the once-per-task cap means a persistent outage still ends in the honest "could not complete" reply. Demonstrated: with the matcher off, a synthetic 503 passes with the rule and fails without it.
retry every failed task AUDIT_RETRY_FAILED_TASK, off: flipping it changed 8 existing tests (runaway loops end escalated, rejected plan steps get retried).
learned ranking AUDIT_EXPERIENCE_LEARNING, off. Wired and unit-tested, but not demonstrable as an outcome benefit in Aielia — the chosen strategy does not change what the model sees.
stall rule a run that stalls (completion velocity, a strategy loop, a recurring failure or risk oscillation) gets a global rebuild of the task graph, otherwise a local replan. The Trajectory Supervisor, if enabled, is consulted only at that stall.

A Adaptive layer control

One consolidated LLM call, made before the harness runs, that classifies the turn (in the code, the turn-intent classifier). Its judgments decide whether the harness runs at all, how the turn is planned, whether it needs approval, and whether the Reviewer Pass's adversarial lens runs. A greeting needs none of it; a risky multi-step request needs all of it.

Files: turn-intent-classifier.ts · turn-policy.ts · turn-interpreter.ts
riskLevel LOW / MEDIUM / HIGH, or UNKNOWN when the classifier call fails or can't be parsed (treated as HIGH and requires approval), with a stated riskReason. Drives the approval gate and Control State, and the depth of the Reviewer Pass: its adversarial lens only runs on a non-LOW-risk turn or one with three or more tasks.
isTrivial only meaningful when riskLevel is LOW — true turns every harness layer off: the reply goes straight back and HarnessRuntime.run() never runs (and no next-step options are proposed).

🤖 Semantic contradiction backstop

An LLM check that compares new beliefs against the ones already on record, by meaning rather than wording. Since 2026-09-28 it is the contradiction detector Aielia uses by default: the harness's lexical negation-pair detector is switched off in the CLI and desktop app.

Files: contradiction-checker.ts · lexical/lexical-mode.ts
semantic pass (default) an LLM call when new check-worthy beliefs are added, in the harness and again on memory facts (AUDIT_SEMANTIC_CONTRADICTION=0 turns it off); task-completion trail beliefs are never checked
lexical pass (opt back in) ASSISTANT_LEXICAL_MODE=enabled restores the keyword detector (build passed/failed, file exists/missing…) and the skip that avoids the LLM call when every new belief is already lexically structured
severity a found contradiction is recorded as MEDIUM; with AUDIT_SEMANTIC_CONTRADICTION_SEVERITY=1 (off) the same call can grade it HIGH

Evaluation: verified — on its layer conversation the turn passes with the check on and fails with it off, in 3 of 3 runs, and the check's own LLM call appears only in the ON arm.

🤖 Semantic failure-mode backstop

Matches observed symptoms against the curated failure-pattern library by meaning, not exact wording — e.g. "the request took too long and timed out" matches a curated "request timed out" symptom.

Files: failure-mode-matcher.ts

Layered on Recovery (Layer 10)'s pattern library — one LLM call, asked about a task only after it has failed, and not again once it has produced a match for that task (it sees the task's first failure). By default it is the only matcher: the exact-substring match is switched off with the other lexical checks (ASSISTANT_LEXICAL_MODE=enabled restores it). A match with confidence 0.7 or higher and a curated preferred strategy re-queues the failed task. Its escalation hook is now gated per call, so an adaptive layer policy can turn it on mid-turn rather than only at the start.

Evaluation: demonstrated on every backend for one pattern — a transient model-call error (a synthetic 503) becomes a failed task, the match re-queues it, and the turn passes where the control fails. One seed each. The other three curated patterns have no demonstrated trigger.
🤖 Semantic review-checker

Checks whether a proposed action genuinely conflicts with a high-confidence belief or an active hypothesis's predicted observation — a real logical conflict, not just topical overlap.

Files: review-checker.ts

Runs in Execution (Layer 8)'s review gate after the lexical dimensions pass (those are off by default in Aielia), and checks against high-confidence beliefs, known facts and hypothesis predictions. Advisory: a conflict is surfaced as a heads-up, not a block. AUDIT_SEMANTIC_CHANGE_REVIEW, on by default.

Evaluation: fires and is wired end to end, but no benefit shown — across six pilots the model caught the conflict without it.
🤖 Context compression

Keeps a long conversation inside the model's context window. Once the transcript passes 40 messages or 20,000 characters, everything but the last 10 messages is folded into one message. By default that message keeps only the first 200 characters of each older message, so a detail deep inside an early long message is lost. Not one of the 11 counted layers.

Files: transcript-compaction.ts · semantic-compaction.ts
opt-in AUDIT_SEMANTIC_COMPACTION=1: one LLM call summarizes the older part instead, keeping names, numbers, dates, decisions and constraints; any failure falls back to the truncated form. On one matched pair it kept a detail the default lost; cost and quality on messier sessions are unmeasured, so it stays off.
🤖 Plan persistence

A durable, user-approved multi-task plan (drafting, awaiting approval, active, then done or abandoned) that survives across turns and crashes and is cleared by /new — separate from the harness's own per-turn task graph (Layer 7), which starts fresh each turn.

Files: plan-store.ts · plan-builder.ts
🤖 User-fact memory

Facts stated in one conversation are extracted and carried into future ones. Each turn the model is shown a block of facts that fits a character budget (memoryBudgetChars, default 4000), most important first, instead of only the 20 most recent. This budgeted render is on by default (AUDIT_MEMORY_BUDGETED_RENDER=0 restores the old path). Everything marked opt-in below is off by default.

Files: fact-extraction.ts · memory-service.ts · memory-governance.ts · episodic-digest.ts · memory-reviewer.ts · memory-consolidation.ts · recall-tool.ts
confidence a fact you assert directly is kept if durable. A model-inferred one is kept only at high confidence, queued for /memory confirm at medium, and session-only at low (shown as unconfirmed).
corrections (default) a fact with a key replaces the earlier fact for the same attribute, and the old one goes to a retired store. Shown on one corrections scenario, 3 of 3 seeds. Not measured: key stability, so a changed attribute can be stored under a different key and miss the replacement.
controls (default) /memory status shows store size against budget; /memory forget removes a fact; /memory off stops all memory writes and leaves existing facts readable. A forget request made in plain language is only staged for your approval.
write gate AUDIT_MEMORY_WRITE_GATE, opt-in. A model check redacts secrets and flags instruction-like text before a fact is stored, and refuses to store when the check cannot run. The base model already resisted in the one scenario run, so no outcome gain is shown.
audit log AUDIT_MEMORY_AUDIT_LOG, opt-in. Enables /memory history and /memory undo. Undo exactness is unit-tested only.
episodic digest and recall AUDIT_EPISODIC_DIGEST and AUDIT_RECALL_TOOL, opt-in. A handoff digest is written at the session edge, and the model can read digests through a read-only recall_memory tool. Shown on one scenario, 2 seeds. Adds a model call per session edge.
reviewer AUDIT_MEMORY_REVIEWER, opt-in. A post-turn pass proposes cross-turn memories. Its writes are staged for /memory confirm unless memoryWriteMode is auto. In auto mode it passed 2 of 2 seeds; the default staged mode failed both arms in its first gate and was then fixed.
consolidation AUDIT_MEMORY_CONSOLIDATION, opt-in; needs the audit log. It proposes merges and archives, applied only on /memory consolidate accept. Not measured as an outcome; one all-flags run cost about 10-40% more.
🤖 Spend cap

checkSpendCap() runs once per new turn, before any LLM call, and refuses it once the session's cumulative cost (sessionCostLimitUsd) or its count of recorded turns and background memory calls (sessionCallLimit) reaches the ceiling. The ledger persists per session across /new and restarts. Neither limit is set by default, and a running turn and an approval resume are never interrupted. A model with no known price counts as $0. No harness-core equivalent — the harness itself doesn't track cost.

Files: spend-cap.ts · model-pricing.ts
🤖 Undo log

Every applied file write or shell command is recorded (the newest 20 are kept), so it can be reverted. A write over a binary file, or a shell run in a workspace too large to snapshot (over 2,000 files), is marked not undoable with the reason. Files skipped (binary, over 1 MB, ignored directories) are listed as unsnapshottable and the revert is flagged incomplete. Emails are not logged. A revert is staged for your approval via /undo-action.

🤖 Mid-turn steering

A message sent while a turn is still running is absorbed into that turn instead of waiting behind it. Every message ends in exactly one of two places: applied to the answer being written, or run as its own follow-up turn.

A message is applied to the current answer only if it is classified before the model's next call: on its layer conversation an early correction produced the right answer in one turn, cheaper than queueing; a message that arrives while claude-cli's single model call is running becomes a follow-up turn. An earlier 11-scenario comparison was graded lexically and has not been reproduced. An earlier design pushed the raw message into the harness's lexically enforced constraint fields; it dropped asks and was replaced by the note-or-follow-up design above.

🤖 Hierarchical goal graph

A persistent goal graph across turns: each root goal is a thread, so concurrent goals, paused work and finished work stay inspectable instead of collapsing into a single plan.

identity open threads are the candidates (a finished goal is not reopened). A match on a blocked thread keeps it blocked. Ambiguity or a failed call starts a new thread rather than guess, since a missed match costs an extra thread but a wrong one puts work on the wrong goal.

🤖 Next-step options

After a full turn, Aielia proposes up to three concrete things you could do next and shows them under the reply, the way Claude Code offers prompt suggestions. They are shortcuts, never a required choice: you can always just type your own message.

no options a trivial one-liner, a paused or escalated turn, or a turn with nothing concrete to follow up gets none, and makes no extra call.
cost one extra LLM call per full turn, folded into the turn's usage and spend cap. If it fails, the turn is unaffected and simply shows no options.
Status on by default in the CLI and chat-ui since 2026-09-23 (ASSISTANT_GOAL_GRAPH_SUGGEST=disabled turns it off). The assistant library itself defaults it off, so embedders and benchmarks make no extra call.
