BUILD A HARNESS · SYSTEM ANATOMY

Inside the harness.

A harness is a governance and reliability control plane around an autonomous agent: the agent has intelligence, the harness has authority. The agent proposes; the harness decides what's allowed to happen next; evidence decides whether the result is accepted. Every turn walks the same eleven layers of it, in the same order, whether it's Aielia (Build A Harness's own reference chat agent) or a flow drawn on the canvas. This is that loop — World Model through Reviewer Pass — read out of the harness source (packages/harness, with its Python twin in adapter/harness/). Click any layer below to open its internal flowchart.

THE LOOP

Eleven layers, in the order they run.

The chart follows one non-trivial turn in the order the harness actually executes it. Before the loop the assistant's adaptive layer control decides how much of the harness the turn needs, and the harness initializes its state. Then every iteration thinks (contradiction check, hypotheses, diagnostics, control state, planning), acts (the execution gate, the tool call, then the evidence and world model are updated from what came back) and checks (diagnostics and control state re-scored, verification, and recovery if the task failed), and repeats until every task is complete. The reviewer pass runs once after the loop, and again if it reopens a task; then the answer is validated. Layers keep the numbers used in the code and docs, drawn in execution order. Click any layer, or any 🤖 hook, for its own flowchart.

Skipped on trivial turns

A single consolidated call up front (adaptive layer control) (risk, triviality, decomposition, plan-abandonment, plan-template matching) flags a genuinely self-contained factual one-liner as trivial — that reply returns directly and none of the eleven layers above run. Everything else walks the full loop. See Aielia for how this applies turn by turn in the reference chat agent.

AROUND THE LOOP

One turn, everything on.

The eleven layers above run inside a single proposer loop (ASSISTANT_ONE_LOOP, on by default): the harness drives one tool-calling iteration at a time instead of reviewing a finished reply. Four mechanisms wrap that loop. The diagram shows one turn with all of them enabled: the goal graph decides which thread has focus, the steering channel is polled at the start of every iteration, the Supervisor is consulted only if an iteration stalls, and once the reply is out, up to three next-step options appear under it. Click any card, or any 🤖 hook in the chain above, for its flow.

What is on by default

All four are on by default in Aielia: the one-loop proposer (ASSISTANT_ONE_LOOP), the Trajectory Supervisor (HARNESS_TRAJECTORY_SUPERVISOR), and mid-turn steering with the goal graph (ASSISTANT_GOAL_GRAPH), and the next-step options (ASSISTANT_GOAL_GRAPH_SUGGEST). Each has an explicit disabled (or 0) escape hatch. With steering and the goal graph disabled, a message sent during a turn waits in line exactly as it did before, and no goal graph is kept.

Also by default: the lexical checks under the semantic layers are off (ASSISTANT_LEXICAL_MODE=disabled since 2026-09-28, so contradiction, failure matching and injection detection run on the LLM check alone), the grounding check behind a verified label is on, and so is the semantic judge for caller constraints. Also on: the single retry of a system-error failure (AUDIT_RETRY_SYSTEM_ERRORS), semantic failure matching, and resuming a stuck plan only when the message continues it. Off by default, behind AUDIT_* flags: semantic hypotheses, reviewer revision, semantic transcript compaction, experience learning, source reliability, the per-step task-completion check, contradiction severity, code plan templates, retrying every failed task, and ask mode (ASSISTANT_ASK_MODE, which lets the Supervisor and the harness put a structured question to you). The adaptive layer policy is also off: the static policy is the default.

6 Control State

Where it bites in Aielia the harness-level resolver is shown to work at the harness level (4 or fewer executions against 43 without it), but in the assistant its ratio inputs need 3 or more attempted tasks, which the eval notes say Aielia's graphs do not reach. Its effect is delivered instead by a turn-local copy behind the tool-policy gate (a retry loop is denied at the 8th counted failure) and by the stall rule and Trajectory Supervisor for executor failures.

10 Recovery

Six named strategies in a fixed, escalating order — a rollback-and-replan path instead of the run crashing out. In Aielia the strategy picked is mostly bookkeeping (a one-sentence hint reaches the model); what changes the outcome is whether a failed task is retried at all.

Files: recovery.py · replanning.py · memory.py
1 · DIRECT_EDITsmallest targeted fix
→
2 · TRACE_EXECpin down where it broke
→
3 · BROADER_SEARCHwiden context search
→
4 · REIMPLEMENTrebuild the approach
→
5 · MINIMAL_FIXaccept a smaller fix
→
6 · ESCALATEhand off to a human

Past experience can bias which strategy is tried first, but only when experience learning is switched on (AUDIT_EXPERIENCE_LEARNING=1, off by default). Otherwise nothing writes the strategy weights and this fixed order is always used, as it is whenever the experience store is unavailable (INV-10). A failure-mode pattern library gives advisory bias only — it never overrides a caller's own decision.

system-error retry AUDIT_RETRY_SYSTEM_ERRORS, on by default. Each failed execution is tagged system_error (the executor threw, or the tool or model call broke) or exhausted (it ran out of its own iteration budget). After the ladder switches strategy, a system_error task is re-queued once. Exhausted loops, rejected completion checks and failed verification are never retried, and the once-per-task cap means a persistent outage still ends in the honest "could not complete" reply. Demonstrated: with the matcher off, a synthetic 503 passes with the rule and fails without it.
retry every failed task AUDIT_RETRY_FAILED_TASK, off: flipping it changed 8 existing tests (runaway loops end escalated, rejected plan steps get retried).
learned ranking AUDIT_EXPERIENCE_LEARNING, off. Wired and unit-tested, but not demonstrable as an outcome benefit in Aielia — the chosen strategy does not change what the model sees.

A Adaptive layer control

One consolidated LLM call, made before the harness runs, that classifies the turn (in the code, the turn-intent classifier). Its judgments decide whether the harness runs at all, how the turn is planned, whether it needs approval, and whether the Reviewer Pass's adversarial lens runs. A greeting needs none of it; a risky multi-step request needs all of it.

Files: turn-intent-classifier.ts · turn-policy.ts · turn-interpreter.ts
riskLevel LOW / MEDIUM / HIGH, or UNKNOWN when the classifier call fails or can't be parsed (treated as HIGH and requires approval), with a stated riskReason. Drives the approval gate and Control State, and the depth of the Reviewer Pass: its adversarial lens only runs on a non-LOW-risk turn or one with three or more tasks.
isTrivial only meaningful when riskLevel is LOW — true turns every harness layer off: the reply goes straight back and HarnessRuntime.run() never runs (and no next-step options are proposed).
decomposedTasks a multi-step request broken into an ordered task list, or null. Shapes Planning (Layer 7): one task per node instead of a single task.
plan flags isAbandonRequest, matchedPlanTemplate and needsMultiStepPlan: abandon judgment is only asked when a plan is already active; template matching and the durable-plan check only when it isn't. Together they decide whether the turn runs under a tracked, user-approved plan.
isReminderRequest / isBulkReminderRequest folded into requiresApproval the same way
isPlanQuestion a question about an active plan's state is answered from the recorded plan instead of re-running it (by default, only while a step has failed)
continuesPlan with a plan active, whether the message tells the assistant to carry on (a go-ahead, "retry", details for a failed step). Only an explicit false sets a stuck plan aside (AUDIT_STUCK_PLAN_RESUME).
facts and constraints statesDurableFacts (each with a confidence and a durable bit) feed user-fact memory; statedConstraints, lastingConstraints and liftedConstraints feed the constraint judge.
isUnderdetermined read only when the opt-in semantic hypotheses are on (Layer 3)
layer-policy signals needsGrounding, ambiguity, userPosture and pushbackOnPriorTurn ride the same call and are read only by the layer policy.
layer policy layerPolicyMode is static: every layer runs as configured. An adaptive mode exists that would switch layers off per turn, but all eight of its rules are still unproven hypotheses, so it stays off; shadow telemetry records what it would have done, with the real LLM calls and tokens the four escalation hooks spend.

🤖 Semantic contradiction backstop

An LLM check that compares new beliefs against the ones already on record, by meaning rather than wording. Since 2026-09-28 it is the contradiction detector Aielia uses by default: the harness's lexical negation-pair detector is switched off in the CLI and desktop app.

Files: contradiction-checker.ts · lexical/lexical-mode.ts
semantic pass (default) an LLM call when new check-worthy beliefs are added, in the harness and again on memory facts (AUDIT_SEMANTIC_CONTRADICTION=0 turns it off); task-completion trail beliefs are never checked
lexical pass (opt back in) ASSISTANT_LEXICAL_MODE=enabled restores the keyword detector (build passed/failed, file exists/missing…) and the skip that avoids the LLM call when every new belief is already lexically structured
severity a found contradiction is recorded as MEDIUM; with AUDIT_SEMANTIC_CONTRADICTION_SEVERITY=1 (off) the same call can grade it HIGH

Evaluation: verified — on its layer conversation the turn passes with the check on and fails with it off, in 3 of 3 runs, and the check's own LLM call appears only in the ON arm.

A deterministic, harness-state-informed check before each read-only tool call runs — not just advisory classification checked after the fact. Complements pending-action approval above, which already gates write_file/run_shell_command unconditionally regardless of this check.

🤖 Semantic failure-mode backstop

Matches observed symptoms against the curated failure-pattern library by meaning, not exact wording — e.g. "the request took too long and timed out" matches a curated "request timed out" symptom.

Files: failure-mode-matcher.ts

Layered on Recovery (Layer 10)'s pattern library — one LLM call, asked once per failed task, and it sees a task's first failure. By default it is the only matcher: the exact-substring match is switched off with the other lexical checks (ASSISTANT_LEXICAL_MODE=enabled restores it). A confident match re-queues the failed task. Its escalation hook is now gated per call, so an adaptive layer policy can turn it on mid-turn rather than only at the start.

Evaluation: demonstrated on every backend for one pattern — a transient model-call error (a synthetic 503) becomes a failed task, the match re-queues it, and the turn passes where the control fails. One seed each. The other three curated patterns have no demonstrated trigger.
🤖 Semantic review-checker

Checks whether a proposed action genuinely conflicts with a high-confidence belief or an active hypothesis's predicted observation — a real logical conflict, not just topical overlap.

Files: review-checker.ts

Runs in Execution (Layer 8)'s review gate after the lexical dimensions pass (those are off by default in Aielia), and checks against high-confidence beliefs, known facts and hypothesis predictions. Advisory: a conflict is surfaced as a heads-up, not a block. AUDIT_SEMANTIC_CHANGE_REVIEW, on by default.

Evaluation: fires and is wired end to end, but no benefit shown — across six pilots the model caught the conflict without it.
🤖 Context compression

Keeps a long conversation inside the model's context window. Once the transcript passes 40 messages or 20,000 characters, everything but the last 10 messages is folded into one message. By default that message keeps only the first 200 characters of each older message, so a detail deep inside an early long message is lost. Not one of the 11 counted layers.

Files: transcript-compaction.ts · semantic-compaction.ts
opt-in AUDIT_SEMANTIC_COMPACTION=1: one LLM call summarizes the older part instead, keeping names, numbers, dates, decisions and constraints; any failure falls back to the truncated form. On one matched pair it kept a detail the default lost; cost and quality on messier sessions are unmeasured, so it stays off.
🤖 Plan persistence

A durable, multi-task plan that survives across turns and crashes — separate from the harness's own per-turn task graph (Layer 7), which starts fresh each turn.

Files: plan-store.ts · plan-builder.ts
🤖 User-fact memory

Facts stated in one conversation are extracted and carried into future ones. A fact you assert directly is kept if durable; a model-inferred one is kept only at high confidence, queued for /memory confirm at medium, and session-only at low (shown as unconfirmed).

Files: fact-extraction.ts
🤖 Spend cap

checkSpendCap() runs once per turn, before any LLM call for that turn is made, and can refuse the turn outright once the session's cost ceiling (sessionCostLimitUsd) or turn-count ceiling (sessionCallLimit) is reached. Neither is set by default, and a turn already running is never interrupted. No harness-core equivalent — the harness itself doesn't track cost.

Files: spend-cap.ts · model-pricing.ts
🤖 Undo log

Every applied file write or shell command is recorded with what it changed, so it can be reverted. Where content could not be captured (binary, oversized) the entry is marked not undoable and says why. A revert is staged for your approval like any other action.

Files: action-snapshot.ts

🤖 Mid-turn steering

A message sent while a turn is still running is absorbed into that turn instead of waiting behind it. Every message ends in exactly one of two places: applied to the answer being written, or run as its own follow-up turn.

🤖 Trajectory Supervisor

A slow-loop meta-controller that intervenes only when the loop cannot make progress. One LLM call at the stall edge; it never runs on a healthy iteration (INV-22) and never writes control state (INV-21).

REDIRECT_STRATEGY re-queue the failed task so the proposer tries a different route.

GATHER_EVIDENCE a bounded, read-only workspace investigation (INV-23/24/25); its findings are spliced into the proposer's context and the task is re-queued. At most three per run, each capped at 20 tool calls (default 5).

ABORT stop and explain why.
Status on by default in Aielia (HARNESS_TRAJECTORY_SUPERVISOR=0 turns it off). The harness library itself still defaults it off; Aielia resolves its own default in supervisor-flag.ts. A turn that never stalls is identical either way.
🤖 Hierarchical goal graph

A persistent goal graph across turns: each root goal is a thread, so concurrent goals, paused work and finished work stay inspectable instead of collapsing into a single plan.

thread states READY · ACTIVE · BLOCKED · PAUSED · DONE · ABANDONED. PAUSED keeps its partial state and evidence (INV-42); ABANDONED is kept for the audit trail, never deleted.
never selectable a thread still being drafted is never given focus (INV-40); a still-workable ACTIVE thread is never bumped just because others are waiting.
/goals the CLI command and the chat-ui panel show four buckets: freshly computed, carried over, done, and suggested-but-not-committed (drafting).
next steps when a thread reaches DONE, one bounded LLM call proposes follow-ups; high and medium confidence ones are saved on the thread and listed under it in /goals (low confidence is shown for the turn only). They are advice, never tasks.
identity open threads are the candidates (a finished goal is not reopened). A match on a blocked thread keeps it blocked. Ambiguity or a failed call starts a new thread rather than guess, since a missed match costs an extra thread but a wrong one puts work on the wrong goal.
Status on by default since 2026-09-23 (ASSISTANT_GOAL_GRAPH=disabled turns it off; with it off, behaviour is byte-identical to before, INV-43).
🤖 Next-step options

After a full turn, Aielia proposes up to three concrete things you could do next and shows them under the reply, the way Claude Code offers prompt suggestions. They are shortcuts, never a required choice: you can always just type your own message.

CLI type 1, 2 or 3 right after the reply to run that option. Any other input, including a command, drops the options.
chat-ui clicking a chip only fills the composer with that text as an editable draft. It never sends by itself.
typing your own always works, and the composer is never locked to the options.
no options a trivial one-liner, a paused or escalated turn, or a turn with nothing concrete to follow up gets none, and makes no extra call.
cost one extra LLM call per full turn, folded into the turn's usage and spend cap. If it fails, the turn is unaffected and simply shows no options.
Status on by default in the CLI and chat-ui since 2026-09-23 (ASSISTANT_GOAL_GRAPH_SUGGEST=disabled turns it off). The assistant library itself defaults it off, so embedders and benchmarks make no extra call.
