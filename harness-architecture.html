BUILD A HARNESS · SYSTEM ANATOMY

Inside the harness.

A harness is a governance and reliability control plane around an autonomous agent: the agent has intelligence, the harness has authority. The agent proposes; the harness decides what's allowed to happen next; evidence decides whether the result is accepted. Every turn walks the same eleven layers of it, in the same order, whether it's Aielia (Build A Harness's own reference chat agent) or a flow drawn on the canvas. This is that loop — World Model through Reviewer Pass — read straight out of adapter/harness/. Click any layer below to open its internal flowchart.

THE LOOP

Eleven layers, in the order they run.

The chart follows one non-trivial turn in the order the harness actually executes it. Before the loop the assistant's adaptive layer control decides how much of the harness the turn needs, and the harness initializes its state. Then every iteration thinks (contradiction check, hypotheses, diagnostics, control state, planning), acts (the execution gate, the tool call, then the evidence and world model are updated from what came back) and checks (diagnostics and control state re-scored, verification, and recovery if the task failed), and repeats until every task is complete. The reviewer pass runs once after the loop, and again if it reopens a task; then the answer is validated. Layers keep the numbers used in the code and docs, drawn in execution order. Click any layer, or any 🤖 hook, for its own flowchart.

Skipped on trivial turns

A single consolidated call up front (adaptive layer control) (risk, triviality, decomposition, plan-abandonment, plan-template matching) flags a genuinely self-contained factual one-liner as trivial — that reply returns directly and none of the eleven layers above run. Everything else walks the full loop. See Aielia for how this applies turn by turn in the reference chat agent.

AROUND THE LOOP

One turn, everything on.

The eleven layers above run inside a single proposer loop (ASSISTANT_ONE_LOOP, on by default): the harness drives one tool-calling iteration at a time instead of reviewing a finished reply. Four mechanisms wrap that loop. The diagram shows one turn with all of them enabled: the goal graph decides which thread has focus, the steering channel is polled at the start of every iteration, the Supervisor is consulted only if an iteration stalls, and once the reply is out, up to three next-step options appear under it. Click any card, or any 🤖 hook in the chain above, for its flow.

What is on by default

All three are on by default in Aielia: the one-loop proposer (ASSISTANT_ONE_LOOP), the Trajectory Supervisor (HARNESS_TRAJECTORY_SUPERVISOR), and mid-turn steering with the goal graph (ASSISTANT_GOAL_GRAPH), and the next-step options (ASSISTANT_GOAL_GRAPH_SUGGEST). Each has an explicit disabled (or 0) escape hatch. With steering and the goal graph disabled, a message sent during a turn waits in line exactly as it did before, and no goal graph is kept.

A Adaptive layer control

One consolidated LLM call, made before the harness runs, that decides how much harness this turn gets — which layers engage and how deep they go — by classifying the turn (in the code, the turn-intent classifier). A greeting needs none of it; a risky multi-step request needs all of it.

Files: turn-intent-classifier.ts · turn-policy.ts · turn-interpreter.ts
riskLevel LOW / MEDIUM / HIGH, with a stated riskReason. Drives the approval gate and Control State, and the depth of the Reviewer Pass: its adversarial lens only runs on a non-LOW-risk or multi-task turn.
isTrivial only meaningful when riskLevel is LOW — true turns every harness layer off: the reply goes straight back and HarnessRuntime.run() never runs (and no next-step options are proposed).
decomposedTasks a multi-step request broken into an ordered task list, or null. Shapes Planning (Layer 7): one task per node instead of a single task.
plan flags isAbandonRequest, matchedPlanTemplate and needsMultiStepPlan: abandon judgment is only asked when a plan is already active; template matching and the durable-plan check only when it isn't. Together they decide whether the turn runs under a tracked, user-approved plan.
isReminderRequest / isBulkReminderRequest folded into requiresApproval the same way
🤖 Trust-tagging

Untrusted content is wrapped before it ever has a chance to become a belief in World Model (Layer 1).

Files: trust-tagging.ts

🤖 Semantic contradiction backstop

An LLM check layered on top of Contradiction (Layer 4)'s own lexical detector — and skipped whenever that lexical pass already had a fair shot.

Files: contradiction-checker.ts
lexical pass (harness) always-on, free — already covers boolean/system-state claims: build passed/failed, file exists/missing, service available/unavailable
semantic pass (assistant) one LLM call, only for candidates the lexical pass wouldn't confidently classify
all-lexical turn if every new belief already looks lexically structured, the LLM call is skipped entirely — no cost

Evaluation: on the bench — Batch B. Does the semantic pass catch enough conflicts the lexical check misses to pay for the call? See the audit →

🤖 Tool-policy gate

A deterministic, harness-state-informed check before each read-only tool call runs — not just advisory classification checked after the fact. Complements pending-action approval above, which already gates write_file/run_shell_command unconditionally regardless of this check.

Files: tool-policy.ts · tool-control-plane.ts
Tool call proposed
→
evaluateToolPolicy()checked against live ControlState
→
ALLOW / DENY / REQUIRE_APPROVAL
ControlState built fresh each turn and updated after every tool-call outcome (success or failure) via the same gatherEvidence → applyToolReliability → updateWorldModel → resolveControlState sequence the harness core uses — so a developing failure pattern within one turn can trip a real DENY, not just get logged after the fact
ALLOW the default — ControlState permits, or nothing's gone wrong yet this turn
DENY the call is blocked outright, reported back to the model as a tool result
REQUIRE_APPROVAL surfaced as an escalation — a read-only call has no concrete pending mutation to stage the way write/shell do
🤖 Semantic failure-mode backstop

Matches observed symptoms against the curated failure-pattern library by meaning, not exact wording — e.g. "the request took too long and timed out" matches a curated "request timed out" symptom.

Files: failure-mode-matcher.ts

Layered on top of Recovery (Layer 10)'s own pattern-library match — one LLM call, only reached when the lexical match doesn't already resolve it.

🤖 Mid-turn steering

A message sent while a turn is still running is absorbed into that turn instead of waiting behind it. Every message ends in exactly one of two places: applied to the answer being written, or run as its own follow-up turn.

Files: live-steering-channel.ts · scope-urgency-classifier.ts · goal-graph-reconcile.ts · agent-loop.ts (steering notes)
Message while a turn runsthe CLI queue is bypassed; the chat-ui composer stays enabled
→
Steering channela FIFO queue, one per session
→
check_caller_updatesone poll per harness iteration
→
Scope × urgency classifierone bounded LLM call; on any doubt: same goal, new task, deferred (INV-41)
SAME_TASK a correction or refinement of what is being written. Becomes a steering note spliced into the proposer's next LLM call as a user turn, so the model applies it. Nothing is matched by keyword.
SAME_GOAL_NEW_TASK · immediate the same: a note for the answer being written now.
SAME_GOAL_NEW_TASK · deferred waits for the current task to finish, then runs as its own turn.
NEW_GOAL pauses the current thread, mints a new READY one in the goal graph, and the ask runs as the next turn.
CANCEL_CURRENT abandons the active thread and blocks the task graph. What you asked for instead (“never mind, just tell me…”) runs as the next turn.
never dropped anything not applied in place, including a note classified after the last LLM call, is handed back to the caller and runs as an ordinary turn, in arrival order.
Status on by default since 2026-09-23 (ASSISTANT_GOAL_GRAPH=disabled restores the old queue-behind-the-turn behaviour). Compared on 11 mid-turn scenarios against that baseline it matched it on task success at lower cost. An earlier design pushed the raw message into the harness's lexically enforced constraint fields; it dropped asks and was replaced by the note-or-follow-up design above.
🤖 Trajectory Supervisor

A slow-loop meta-controller that intervenes only when the loop cannot make progress. One LLM call at the stall edge; it never runs on a healthy iteration (INV-22) and never writes control state (INV-21).

Files: supervisor.ts · trajectory-digest.ts · supervisor-flag.ts · harness-bridge.ts
cannot_make_progress()the stall edge
→
Trajectory digesta compact summary: failure class, tools tried, recurring records
→
decide() — one LLM calla closed directive set; anything outside it degrades to CONTINUE
→
Directivecarried out by the harness
CONTINUE the fail-safe default — carry on unchanged.
REDIRECT_STRATEGY re-queue the failed task so the proposer tries a different route.
REFRAME_PLAN re-frame the plan around the blocker.
GATHER_EVIDENCE a bounded, read-only workspace investigation (INV-23/24/25); its findings are spliced into the proposer's context and the task is re-queued.
ASK_USER surfaces a structured question instead of guessing.
ABORT stop and explain why.
Status on by default in Aielia (HARNESS_TRAJECTORY_SUPERVISOR=0 turns it off). The harness library itself still defaults it off; Aielia resolves its own default in supervisor-flag.ts. A turn that never stalls is identical either way.
🤖 Hierarchical goal graph

A persistent goal graph across turns: each root goal is a thread, so concurrent goals, paused work and finished work stay inspectable instead of collapsing into a single plan.

Files: goal-graph-store.ts · goal-thread-identity.ts · goal-identity-matcher.ts · goal-thread-scheduler.ts · next-step-proposer.ts · goal-graph-service.ts
Turn classified as a full turntrivial one-liners and resumed turns (approvals, answers) skip everything below
→
Identity matcher: one LLM calldoes this continue an open thread? only asked when one exists; ambiguous never guesses
→
Attach, or start a threada match brings that thread back into focus (the current one is paused, evidence kept); no match starts a new thread
→
Scheduler keeps one thread in focussole writer of the ACTIVE pointer (INV-39); one ACTIVE thread (INV-38)
→
Turn runs on the ACTIVE threadplan mode and drafting are scoped to that thread
→
Evidence synced back; DONE when every task completesthe thread keeps its task graph and evidence between turns; finishing it triggers the next-step proposer
thread states READY · ACTIVE · BLOCKED · PAUSED · DONE · ABANDONED. PAUSED keeps its partial state and evidence (INV-42); ABANDONED is kept for the audit trail, never deleted.
never selectable a thread still being drafted is never given focus (INV-40); a still-workable ACTIVE thread is never bumped just because others are waiting.
/goals the CLI command and the chat-ui panel show four buckets: freshly computed, carried over, done, and suggested-but-not-committed (drafting).
next steps when a thread reaches DONE, one bounded LLM call proposes follow-ups; high and medium confidence ones are saved on the thread and listed under it in /goals (low confidence is shown for the turn only). They are advice, never tasks.
identity open threads are the candidates (a finished goal is not reopened). A match on a blocked thread keeps it blocked. Ambiguity or a failed call starts a new thread rather than guess, since a missed match costs an extra thread but a wrong one puts work on the wrong goal.
Status on by default since 2026-09-23 (ASSISTANT_GOAL_GRAPH=disabled turns it off; with it off, behaviour is byte-identical to before, INV-43).
🤖 Next-step options

After a full turn, Aielia proposes up to three concrete things you could do next and shows them under the reply, the way Claude Code offers prompt suggestions. They are shortcuts, never a required choice: you can always just type your own message.

Files: next-step-proposer.ts · assistant.ts · cli.ts · NextStepChips.tsx
Full turn completesstatus ok, and not the trivial one-liner fast path
→
Proposer: one bounded LLM callyour request + the reply in, at most three options out, most confident first
→
Shown under the replyCLI: a numbered list · chat-ui: chips under the newest reply
→
You choose, or don'tpick one, or type anything else
CLI type 1, 2 or 3 right after the reply to run that option. Any other input, including a command, drops the options.
chat-ui clicking a chip only fills the composer with that text as an editable draft. It never sends by itself.
typing your own always works, and the composer is never locked to the options.
no options a trivial one-liner, a paused or escalated turn, or a turn with nothing concrete to follow up gets none, and makes no extra call.
cost one extra LLM call per full turn, folded into the turn's usage and spend cap. If it fails, the turn is unaffected and simply shows no options.
Status on by default in the CLI and chat-ui since 2026-09-23 (ASSISTANT_GOAL_GRAPH_SUGGEST=disabled turns it off). The assistant library itself defaults it off, so embedders and benchmarks make no extra call.
