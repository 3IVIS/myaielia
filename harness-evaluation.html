We measure whether our own features work.

WHY

"Eleven layers, thousands of tests" proves we built something.
Not that it works.

A harness is a governance and reliability layer wrapped around a model. Everything it adds costs latency and tokens on every turn, and is only worth paying for if it changes outcomes: a stalled run that recovers, a correction that lands, a goal that keeps its own evidence.

Our first pass at this benchmark ran mostly single-turn tasks. That is not the shape these four features are for: steering needs a turn that is still running, the supervisor needs a stall with context behind it, the goal graph needs several goals in flight, and next-step options need a finished piece of work to follow up on. So we took the results down, rebuilt the corpus, and re-ran. This page is the rebuilt result, and it is allowed to come back negative.

HOW WE DECIDE

Six steps. Same loop every time.

Modelled on how ML systems are evaluated: a fixed dataset, a mechanical grader, an isolated independent variable, and a confidence interval on the result.

01 — HYPOTHESIS

Name the bet

Write, in one sentence, the belief the feature encodes — the thing that would have to be true for it to be worth the cost.

02 — ARM

Toggle exactly it

A benchmark arm that flips this one feature and nothing else. Everything else — model, corpus, grader — is held fixed.

03 — STRESS CORPUS

Where it matters or nowhere

A tagged set of tasks built so the feature should show its value here if it shows it anywhere. No delta on its own stress slice means no value.

04 — MEASURE

Three seeds, judge on

Run the matrix at least three times. Report Δ task success, recovery, overconfident-wrong answers, cost, latency and tokens — each with a 95% confidence interval.

05 — VERDICT

Effective, or not — at what cost

Effective, similar or lower cost: positive delta on the stress slice, no regression elsewhere, cost at or below budget. Effective, but costs more: a real gain that comes at a real cost — worth it only if the gain clears the bar. Not effective: no measurable gain, regardless of cost. Underpowered: too little data to say either way — grow the corpus and re-run.

06 — RECORD

The whole story, either way

Not just the number. Where the idea came from, what we expected, what actually happened, and why — as an entry on this page, plus a row in the benchmark doc and the machine report JSON in the repo. Negative results included.

RESULTS

What the runs showed.

Four features, each measured against the same assistant without it, three seeds, Claude Sonnet 5 as both the assistant and the judge. Verdicts come from fixed rules: a gain has to clear its confidence band to count, and a gain that costs more has to be big enough to justify it. “Not yet proven” means we can neither keep a feature on by default with confidence nor cut it. THE CORPORA

Built for each mechanism.

Eight tasks per feature, including controls where the feature should do nothing. The tasks are small on purpose, so a grader can check them without a model's opinion. What makes them relevant is their shape.

MID-TURN STEERING

Pointer chains, with a message mid-way

Eight tasks where each file names the next, so the turn has to keep going. A message arrives while it runs: two corrections, two extra asks, two unrelated questions and two cancels. The control queues the message as the next turn, which is what happens with the feature off.

TRAJECTORY SUPERVISOR

Stalls that arrive late

Multi-turn tasks with a tool failure injected on a later turn, after useful work: pointer chains, a file that only points elsewhere, nested lookups, a stale answer overridden by a newer file, and a turn where the user must supply a detail. Two clean sessions check it stays quiet.

NEXT-STEP OPTIONS

Finished work with an obvious sequel

Open TODO items, failing tests, pending release steps, a missing attachment, a flagged outlier and a config that has a prod twin. Two closed questions are the false-positive controls. There is no arm that produces options without the feature, so the options themselves are graded.

GOAL GRAPH

Goals that interleave

Sessions of three to seven turns: return to a goal after a detour, three similar projects updated out of order, format constraints that belong to one topic, a correction that must survive a detour, and a linear control. No mid-turn messages, so thread tracking is separated from steering.

Two things we changed along the way, both on the result pages. The first steering corpus read independent files, which the assistant batched into one step, so we rebuilt it as chains and kept the superseded reports in the repo. And a first scoring of the next-step run wrongly counted missed options as reply failures, which we fixed before publishing.

REPRODUCE

The whole benchmark is open source.

The task corpus, the mechanical grader, the arm definitions and the runner live in the product repo under packages/aielia/eval/. Every result links to its per-run transcripts, and each run records the model it executed on. The four features run in parallel, one process per feature and seed:

cd packages/aielia
node scripts/run-audit-parallel.mjs \
  --features=steering-live,trajectory-supervisor-midtask,next-step-options,goal-graph-threads \
  --seeds=3 --concurrency=6

FAQ

Questions

Why publish results that aren't flattering?

Because “11 layers, thousands of tests” proves we built something, not that it works. A harness is only worth its latency and token cost if it changes outcomes. The honest way to know is a benchmark that can come back negative or unproven, and we publish it either way.

Why are three of the four not yet proven?

Each has a different reason, and each is on its result page. Mid-turn steering never actually got to absorb a message in flight on the keyless CLI backend we can run without an API key. The goal graph scored 100% with and without it, so the corpus could not separate them. Next-step options landed between our pre-set KEEP and CUT thresholds. “Not yet proven” means what it says: not enough to keep it on by default with confidence, not enough to cut.

Why not an A/B test for next-step options?

Without the feature there are no options to compare. Comparing task success would be meaningless, so we graded the options themselves: how often they named the expected continuation, and how often they appeared where nothing should follow. The thresholds (KEEP at 70% hits with at most 25% false positives, CUT under 40% hits) were fixed before the runs.

Does a feature that doesn't earn its cost get deleted?

No. It stays merged and flag-gated, and the result is recorded rather than overridden. If a later test on a different task shape shows value, the flag can flip. The default reflects the evidence we have.

What model are these run on?

Claude Sonnet 5, with Claude Sonnet 5 as the LLM judge. Both ids are written into every machine report and named on every transcript page.

How does this relate to the architecture page?

The architecture page is the map of what the harness contains, read straight from the source. This page is the record of which of those parts we have put on the scale, and what the scale said.
