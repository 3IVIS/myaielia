CASE STUDY · SEVEN OF THE MOST-USED AI AGENTS

Seven popular agents.
One thin harness, seven ways.

Claude Code, Codex CLI, Cline, Hermes Agent, Kilo Code and OpenClaw all run the same commodity tool-calling loop — as their own docs and independent analyses describe — and Pi strips the loop down to four tools on purpose. Reading the pattern: Across the seven agents, Execution, Memory, and Learning are the only layers where any reaches full coverage — checkpoints for Kilo, Claude Code and Cline on Execution, and Hermes's persistent memory and self-improving skills. Pi reaches full coverage on none, deliberately; so does Codex CLI, whose main strength, an OS-enforced sandbox, lands in the Control State and Execution cells as partial. Reasoning gets zero coverage from all seven. Output & Reviewer Pass has no built-in gate in any of them; Claude Code and Codex let you configure a Stop hook that approximates one, so both rate partial. Of the remaining layers, none is built out to full coverage by any of the seven — they're a patchwork of static substitutes, partial mechanisms, and outright gaps, with World Model and Recovery the only two where all seven have at least something, thin as it is. Which is a fair description of where most production agents are today, popular or not. The Aielia column is the reference point — Build A Harness's own assistant, included to show what the thin layers look like when something actually ships them (Control State at full coverage; Reasoning and the Reviewer Pass partial, since hypothesis generation and revising findings are opt-in and off by default; Verification is partial — only three of its nine checks run in a chat turn); it is the newest and least battle-tested of the eight.

Pi is minimal on purpose.

Pi's empty cells are a design position, not an oversight. Its author argues that with four tools (read, write, edit, bash) and a system prompt under 1,000 tokens, frontier models already know how to be coding agents. Pi lists MCP, sub-agents, permission popups, plan mode, built-in to-dos and background bash as deliberately omitted, and ships extensions, skills, prompt templates and installable packages instead. On permissions its stance is explicit: it runs unrestricted by default and treats prompts as "security theater" unless the agent is sandboxed. That is the opposite bet to a harness that gates actions — so the coverage table above measures Pi against a taxonomy it rejects, not against its own goals.

On its own terms Pi does well. In Databricks' July 2026 benchmark on its internal multi-million-line codebase, Pi with Claude Opus 4.8 sent about 3x less context per turn than Claude Code or Codex (both covered above) and cost less at comparable quality; Databricks calls the benchmark non-comprehensive. Aielia has no comparable coding benchmark — its feature evaluation is being rebuilt and its earlier results are offline — so this comparison is about governance, not which agent is cheaper or better at coding.

See each agent's full, unsimplified step list
Hermes Agent — 9 steps
  1. Generate a task ID if not provided
  2. Append the user message to history
  3. Build or reuse the cached system prompt
  4. Check whether preflight compression is needed (>50% context full)
  5. Build API messages from conversation history
  6. Inject ephemeral prompt layers (budget warnings, context pressure)
  7. Apply prompt caching markers (Anthropic)
  8. Make an interruptible API call
  9. Parse response: execute tool calls and loop to step 5, or persist + return
Kilo Code — 7 steps
  1. User gives a task, selects an agent mode (code/ask/plan/debug)
  2. Kilo assembles context: system prompt, auto-found files, @-mentions, AGENTS.md
  3. Prompt + tools sent to the configured model via the Kilo Gateway
  4. Model replies with reasoning plus typically one tool call
  5. State-changing actions pause for user approval unless auto-approved
  6. Approved action executes; result captured
  7. If complete, present for review; else append observation and loop to step 3
OpenClaw — 7 steps
  1. Intake — Gateway RPC/CLI validates params, returns {runId, acceptedAt} immediately
  2. Queue & resolve — serialize via per-session + global queues, resolve model/auth
  3. Session & workspace prep — resolve workspace, load skills, inject bootstrap files
  4. Prompt assembly — base + skills + bootstrap context, token limits enforced
  5. Model inference ⇄ tool execution — stream text/tool-call deltas, execute, repeat
  6. Reply shaping — assemble final payload, filter internal tokens
  7. Persist & emit — write transcript to JSONL, emit lifecycle:end
Claude Code — 3 phases, as documented
  1. Gather context — search and read files, read CLAUDE.md, auto memory and git state
  2. Take action — edit files, run commands, call tools; file contents are snapshotted before each edit
  3. Verify results — run tests or re-check; each tool result feeds the next decision, repeating until the task is done
  4. You can interrupt or queue a correction at any point; context is compacted automatically near the limit
Codex CLI — 5 steps
  1. Assemble the prompt: instructions, tools and the full conversation history (AGENTS.md included)
  2. Send a stateless request to the Responses API — full history every time, no previous_response_id
  3. Stream the response and process its events
  4. If the model emits a function call, run the tool under the sandbox mode and approval policy and append the result
  5. Loop until the model replies in plain text; compact the conversation automatically past a token threshold
Cline — 6 steps
  1. Start a task in Plan mode (read-only) or Act mode
  2. Load rules (.clinerules, AGENTS.md; path-conditional ones activate on matching files) and @-mentioned context
  3. Send a model request
  4. For each tool call, ask for approval unless that category is auto-approved; the model flags which commands need it
  5. Commit a shadow-git checkpoint after each tool use
  6. Append the tool result and repeat until complete; summarize automatically near the context limit
Pi — no step list published

Pi's docs describe four core tools (read, write, edit, bash), JSONL session trees, compaction and extension hooks, not a numbered step-level loop, so none is reconstructed here.

Hermes Agent

Its loop is a refined ReAct implementation — Observation → Reasoning → Action — the same call-model / run-tools / append-results shape Claude Code and most agents use. Nous's own framing puts the differentiation in memory and self-improving skills, not the loop.

Kilo Code

Kilo began as a fork of Roo Code, itself a fork of Cline; since April 2026 its VS Code extension and CLI run on an OpenCode-based core. Either way the loop is a standard tool-calling loop, and Kilo's stated edge is pricing, model breadth and reliability plumbing, not the loop.

OpenClaw

Independent architecture write-ups describe OpenClaw's runtime as "just a ReAct loop, a filesystem, sessions, and plain API calls" — the simplicity is deliberate, and by broad agreement the loop is not where its traction comes from.

Pi

Pi doesn't pretend the loop is special. It keeps it as small as it can, with four tools and a system prompt under 1,000 tokens, and treats permissions, planning and sub-agents as optional extensions rather than core.

Claude Code

Its own docs say the agentic loop is "powered by two components: models that reason and tools that act," and call the layer around the model that supplies tools and manages context "the agentic harness." The loop is three phases — gather context, take action, verify results — and the differentiation is the machinery around it: permissions, checkpoints, hooks, subagents and memory.

Codex CLI

OpenAI describes the agent loop as "the core logic in Codex CLI that is responsible for orchestrating the interaction between the user, the model, and the tools the model invokes." It is a plain call-model / run-tool / append-result cycle; what Codex invests in around it is an OS-level sandbox and an approval policy.

Cline

Cline's SDK describes its loop as "model request → tool calls, if any → tool results → repeat until complete." Its distinctive layer is human-in-the-loop control — Plan / Act modes, per-category approvals and a checkpoint after every tool use — and the loop itself is the commodity part.

FAQ

Questions, answered.

Why compare Claude Code, Codex CLI, Cline, Hermes Agent, Kilo Code, OpenClaw and Pi specifically?

They're seven of the most-used AI agents running today — six open-source (Codex CLI, Cline, Hermes, Kilo Code, OpenClaw, Pi) and Claude Code, which is proprietary — each with public documentation detailed enough to map against a common harness taxonomy. Claude Code, Codex CLI, Cline, Hermes, Kilo Code and OpenClaw run a conventional tool-calling loop, per the projects' own docs and independent analyses. Pi is included as the deliberately minimal counterexample: it leaves most governance layers out on purpose.

Which of the seven has the best harness?

None covers more than 2 of 11 canonical layers at full strength. Hermes leads on Memory and Learning. Kilo Code, Claude Code and Cline reach full coverage on Execution only, all through reversible edits (checkpoints). Codex CLI covers none at full strength; its main strength is a default OS-enforced sandbox (Seatbelt on macOS, bubblewrap on Linux). Both it and Claude Code had permission-bypass CVEs disclosed in 2026 (Codex, Claude Code). Pi covers none at full strength by design, yet was the most cost-efficient harness in Databricks' July 2026 benchmark. OpenClaw leads on reach, but its broad action surface lines up with its documented security incidents — critical CVEs including a 9.9-severity privilege-escalation-to-RCE flaw and an 8.8 one-click RCE, plus a marketplace campaign that disclosed 341 malicious skills in a single sweep.

What is the 11-layer harness architecture?

The canonical architecture used across Build A Harness: Caller State, World Model, Reasoning, Control State, Planning, Execution, Verification, Recovery, Memory, Learning, and Output & Reviewer Pass. Full definition →

Where does Build A Harness fit in?

Build A Harness implements all 11 layers as drawable, composable canvas nodes — so you can build the layers these seven agents leave thin (Reasoning, a tiered Control State, Verification, Output & Reviewer Pass) without writing that infrastructure yourself.

THE RUNNABLE ALTERNATIVE

Build A Harness — Aielia.

The mapping above is a taxonomy exercise unless something actually ships those layers. Aielia — Build A Harness's own assistant — wires the 11-layer harness into every non-trivial turn (Hypothesis, Diagnostics and experience learning are dormant or opt-in by default), and is the same class of tool as the seven above: an everyday chat/coding assistant you install and talk to.

  • Control State — full, not partial. Every read-only tool call is checked against a per-turn control state (built from that turn's tool outcomes) before it runs: deterministic ALLOW / DENY / REQUIRE_APPROVAL, not an advisory hint. A send / delete / pay / post request is classified as needing approval and pauses before the action runs; a classifier failure also resolves to approval-required.
  • Output & Reviewer Pass — present, advisory. A two-lens review (implementer, reviewer) runs on every turn, with a third, adversarial lens added on consequential or multi-step turns; an abstraction-fit check and output-contract validation run before a reply leaves the harness.
  • Verification — partial, and honest about it. Nine verification checks are defined, but only two normally return a result in a chat turn (evidence sufficiency and output contract). The others report SKIPPED rather than faking a pass — syntax, unit and integration have no execution boundary to check, consistency is handled by the contradiction layer instead, and goal correctness needs model-level judgment.
  • Fail-safe risk handling. A classifier error or unparseable response resolves to "requires approval", never a silent default to low-risk.
  • Untrusted-content boundary. Web results and shell output are wrapped as data the model is instructed never to follow as commands.
  • Crash-safe mid-turn. A turn that dies mid-flight resumes from its last checkpoint; a checkpoint that keeps crashing on replay is discarded automatically after two attempts.

Honest caveats: Aielia is the newest of the eight and the least battle-tested. It is an early-stage project (package v0.3.x), not an audited security product — the harness reduces the blast radius of a bad decision, it does not eliminate it. Apache 2.0, provided as-is.
